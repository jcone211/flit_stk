# 上下文压缩与跨轮数据保留机制

> 分析日期：2026-09-06
> 分析背景：对照 Codex 实验性功能（笔记 + 可搜索历史替代反复压摘要），评估 flit_stk 项目中是否存在类似策略。

---

## 一、概述

大型语言模型的上下文窗口有限，当对话变长时，必须压缩历史信息以控制 token 消耗。传统做法是每轮把历史反复压成摘要，但这样做会导致前面的一些细节在不断压缩中丢失。

Codex 近期更新了一个实验性功能，将上下文压缩换成 **「笔记 + 可搜索历史」** 的复合策略：笔记跨上下文窗口保留，需要细节时直接回去搜索之前的消息和工具结果。

**flit_stk 项目不仅实现了这一策略，而且做得更精细、更安全**。本文档详细对比两者的设计思路，并展示项目的具体实现。

## 三、flit_stk 减少 Token 消耗的策略全景

flit_stk 的上下文管理体系包含 **四层** 机制，从静态约束到动态驱逐再到跨层保留，构成一个完整的 token 预算控制闭环。

### 3.1 第 1 层：静态消息/工具结果截断——硬约束

```
ai/core/ai_state.js
```

| 常量 | 值 | 作用 |
|:---|:---|:---|
| `MAX_MESSAGES` | 100 | 聊天消息总条数上限 |
| `MAX_MESSAGE_CHARS` | 10000 | 单条消息内容字符上限 |
| `MAX_TOOL_RESULT_CHARS` | 20000 | 单个工具结果全局硬顶 |
| `TOOL_RESULT_CHARS` | (按工具分级) | 摘要类工具 5000–8000，数据库 10000 |
| `MAX_ROUND_TOOL_CHARS` | 16000 | 单轮全部工具结果总预算 |
| `DEFAULT_TOOL_RESULT_CHARS` | 12000 | 未列入分级的工具兜底上限 |

作用：在工具执行阶段即刻截断过长的返回，避免大块数据送入上下文。

### 3.2 第 2 层：动态驱逐——evictToolResults

```js
// ai/ai.js: evictToolResults(apiMessages, provider)
// 每轮构建 requestMessages 前调用
```

- **预算口径**：按当前所用模型的最大上下文 token 数动态估算  
  - 勾选「1M」→ 1,000,000 token  
  - 未勾选 → 256,000 token  
  - 通过 `estimateTokens()` 中英混合估算（东亚字符 0.7 token/字，其余 0.25 token/字）
- **驱逐策略**：按「最旧优先」驱逐工具结果消息（只改 content，保留 role/tool_call_id 配对）
- **保护规则**：末尾连续的 tool 消息 = 最近一轮结果，**绝不驱逐**
- **可见反馈**：发送按钮左侧环形指示器实时显示上下文占比

### 3.3 第 3 层：手动压缩——/compact

```js
// ai/ai.js: handleCompact / applyCompact
```

- 当模型上下文接近上限时，**用户可点击「压缩」按钮或输入 `/compact`/`/压缩`**
- 底层逻辑：一次非流式模型调用把整段会话压成一条摘要
- 摘要以 `kind:'compact_note'`（role=user）替换历史
- UI 只显示一行提示，模型仍然能看到完整摘要
- 目的是在极端场景下提供最后一层的压缩兜底

### 3.4 第 4 层：跨轮上下文保留——隐藏条目（核心创新）

这是本文的重点，也是与 Codex 实验功能最对标的部分。
## 四、跨轮上下文保留的隐藏条目机制

### 4.1 为什么需要隐藏条目

**核心问题**：工具（function calling）的原始返回只在**一次用户提问内的 function-calling 循环**中有效。下一条用户消息到达时，上下文按 `{role, content}` 从 `state.chatMessages` 重建：

- tool 消息和 assistant.tool_calls 都不落库（协议要求两者成对，缺一个就 400）
- 模型在下一轮完全看不到上一轮工具返回了什么

```js
// ai/ai.js 文件头易踩坑第 11 条
// tool 原始返回不跨轮：chatMessages 只存 user/assistant 正文 + 两条隐藏条目
// 不要把真正的 tool 消息塞进 chatMessages——OpenAI 协议要求 tool 消息紧跟同名 tool_call_id
```

**旧版教训**（`docs/debug.txt`）：模型跨轮时看不到工具原始返回，凭空补了 7 根 K 线。

### 4.2 隐藏条目之一：tool_trace 账本

**自动记录，系统行为**。每轮 function-calling 结束后，`pushToolTrace()` 自动落一条账本：

```js
// ai/ai.js:540-556
function pushToolTrace(calls) {
    const list = (calls || []).filter(c => c && c.name && c.name !== 'load_tool_group');
    if (!list.length) return;
    // ... 格式化工具调用信息
    const entry = pushHiddenEntry('tool_trace', TOOL_TRACE_HEAD + '\n' + body, {
        calls: shown.map(c => ({ name: c.name, ok: c.ok === true })),
    });
    trimHiddenEntries();
}
```

**账本包含信息**：
- 调用了哪些工具
- 参数概览
- 耗时
- 成功还是失败及失败原因
- **load_tool_group 不记**（常驻工具无记录价值）

**容量控制**：
- 单条上限：`MAX_TRACE_CHARS = 900`
- 单轮最多列：`MAX_TRACE_CALLS = 12`
- 保留轮数：`MAX_KEEP_TRACES = 2`（只留最近 2 轮）

### 4.3 隐藏条目之二：retained_data 数据便签

**模型主动调用，按需保留**。模型通过常驻工具 `retain_tool_data` 登记本轮最重要的原始数据：

```js
// ai/core/ai_tools.js:923-957（简化）
retain_tool_data: {
    // 参数：tool（工具名）、note（用途说明）
    // 只能登记本轮真实返回且成功的工具结果
    // 取数失败、本轮没调过的工具一律拒收
    // 同工具重复登记只留最新一份
    // 总量超 MAX_RETAINED_TOTAL / 条数超 MAX_RETAINED_ENTRIES 丢最旧
}
```

**登记成功后**，`pushRetainedNotes()` 在每轮结束将排空的便签落成隐藏上下文：

```js
// ai/ai.js:575-589
function pushRetainedNotes() {
    const notes = state.pendingRetains || [];
    // ... 为每条便签生成带时间戳的来源说明
    pushHiddenEntry('retained_data', head + src + n.text, { source: n.tool, chars: n.text.length });
    trimHiddenEntries();
}
```

**容量控制**：
- 单条上限：`MAX_RETAIN_CHARS = 3000`
- 同时保留条数：`MAX_RETAINED_ENTRIES = 3`
- 总字数上限：`MAX_RETAINED_TOTAL = 6000`

### 4.4 隐藏条目的共同特征

两类条目统一以下列方式管理：

```js
// ai/ai.js:558-569
function pushHiddenEntry(kind, content, meta) {
    const entry = {
        role: TRACE_MESSAGE_ROLE,   // 'user'（统一用 user，避免部分供应商不接受 system）
        kind,                        // 'tool_trace' | 'retained_data'
        content,
        ts: Date.now(),
        uid: genUid('m'),
        ...(meta || {}),
    };
    state.chatMessages.push(entry);
}
```

- **不弹气泡、不渲染到对话区**（`renderHistory` 只打一行摘要）
- **不进用户可见正文**
- **走线前由 `toWireMessage` 剥掉内部字段**（kind/evicted/chars），只发协议字段
- **`trimHiddenEntries` 统一裁剪**（条数/总量超限丢最旧）

## 六、安全机制：防编造 Guard

这是 flit_stk 比 Codex 实验功能走得更远的亮点——模型不能随意向隐藏上下文写入数据。

### 6.1 登记安全限制

`retain_tool_data` 有三道防线：

```
1. 只接受本轮已调用且成功的工具
   → 取数失败的调用不得登记（不能把报错当数据留一份）
   → 本轮没调过的工具不得登记（只能凭真拿到的原文登记）

2. 只接受工具真实返回的原文
   → 模型不能自己写自定义内容进隐藏上下文
   → 防止模型把编造的数字「登记」成事实

3. 同工具重复登记只留最新一份
   → 不能用旧数据冒充当前结果
```

```js
// 安全验证逻辑（ai/core/ai_tools.js）
const src = hits[hits.length - 1];
if (!src.ok) return { error: `${tool} 本轮没有取到数据，无内容可保留` };
```

### 6.2 跨轮证据验证

`hasPriorQuoteEvidence()` 在 guard 决策时被调用，检查两类隐藏条目中是否有真实的行情数据来源：

```js
// ai/ai.js:612-617
function hasPriorQuoteEvidence() {
    return state.chatMessages.some(m =>
        (m.kind === 'retained_data' && QUOTE_TOOLS.has(m.source))
        || (m.kind === 'tool_trace' && (m.calls || []).some(c =>
            QUOTE_TOOLS.has(c.name) && c.ok === true)));
}
```

### 6.3 Guard 三态决策

```js
// ai/core/ai_guard.js: decideQuoteGuard({ text, topicIsQuote, refusal, retried })
```

| 场景 | 动作 | 说明 |
|:---|:---|:---|
| 无编造信号 | `pass` / `note` | 正常提交 / 工具拒绝后转述原因 |
| 初犯 + 无拒绝证据 | `correct` | 注入强制纠正，再来一轮 |
| 初犯 + 有拒绝证据 | `drop` | 工具已拒绝仍编造数值，直接丢弃正文 |
| 再犯 + 强价格信号 | `drop` | 纠正后仍编造，丢弃正文 |
| 再犯 + 弱信号（表格+话题） | `pass_warn` | 放行但加一行免责提示 |

## 八、总结

**flit_stk 项目不仅有 Codex 实验功能中描述的「笔记 + 可搜索历史」策略，而且实现更为成熟和安全：**

1. **模型主动登记**：`retain_tool_data` 让模型自己判断哪些原始数据值得跨轮保留，不是被动压缩
2. **双重隐藏上下文**：账本（做了什么）+ 便签（拿到了什么数据）分开管理，各司其职
3. **严格防编造**：三道登记防线 + 跨轮证据验证 + 三态 guard 决策，杜绝模型编造数据
4. **多级预算控制**：静态截断 → 动态驱逐 → 手动压缩 → 隐藏条目，四层协同工作
5. **可观测性**：DEBUG 模式下记录 `tool_trace` / `retained` / `guard` 事件，便于排障

**一句话概括**：如果要在 Codex 和 flit_stk 之间做对比，flit_stk 的策略不是「实验性功能」，而是**已经投入生产验证的核心机制**——对应回归测试中 167 项断言（R1、C9、C10、G1-G2），并且有实际 bug（debug.txt 中模型编造行情数据）驱动设计。
