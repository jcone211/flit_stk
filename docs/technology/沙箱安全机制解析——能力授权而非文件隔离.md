# 沙箱安全机制解析——能力授权而非文件隔离

> 分析日期：2026-09-06
> 说明：本文澄清项目中「沙箱安全机制」的实际含义，对比传统 OS 级沙箱的差异，并详细拆解多层访问控制架构。

---

## 一、引言：项目自称「沙箱」，但与传统沙箱有何不同？

在 `README.md` 和架构图中，flit_stk 将自己描述为**受 DeepSeek Harness 架构启发的「沙箱隔离」系统**。但这个"沙箱"并**不**等同于传统意义上的 OS 级沙箱。

### 传统沙箱（典型实现）

| 技术 | 原理 | 文件系统隔离 |
|:---|:---|:---|
| **Docker 容器** | Namespace + cgroups | 完全独立的文件系统树 |
| **chroot/jail** | 改变进程根目录 | 进程只能看到 jail 内的文件 |
| **Firejail / AppArmor** | LSM + 路径白名单 | 按路径规则限制读写 |
| **虚拟机** | 硬件虚拟化 | 独立的 Guest OS 文件系统 |

**共同特征**：在 OS 层面开辟一块**文件权限隔离的空间**，进程无法逃逸到宿主机文件系统。

### flit_stk 的实际安全模型

flit_stk 的"沙箱"**不是**在本地创建一个隔离的文件系统命名空间，而是通过 **浏览器 API + 本地 HTTP 服务 + 路径检测 + 程序白名单** 等多层机制，实现**以能力（capability）为基础的访问控制**。AI 能访问什么、不能访问什么，取决于：

1. 用户通过**点击授权**（Chrome FSA 手势）授予了哪些目录
2. `flit_bridge` 的**程序白名单**允许执行哪些命令
3. 代码层**路径检测**能否通过（防目录穿越）
4. 模型层**输出 Guard** 是否放行内容

这更像一套 **多层能力授权与内容过滤系统**，而非传统意义上的沙箱隔离。

## 二、架构全景：八层安全机制

```
① Chrome Extension Sandbox（浏览器进程隔离）
  ② Chrome FSA 用户手势授权（目录访问必须用户点击确认）
    ③ 路径穿越防护（相对路径过滤 . / .. / 空段）
      ④ 写约束（AI 只能写 flit/ 目录）
        ⑤ flit_bridge 访问控制（127.0.0.1 本地回环）
          ⑥ 程序白名单（仅限 docker/git/node/npm/psql）
            ⑦ SQL 只读（仅 SELECT/WITH/EXPLAIN）
              ⑧ 输出 Guard（三态拦截编造内容）
```

## 三、各层机制详解

### 第 1 层：Chrome Extension Sandbox（浏览器级进程隔离）

**来源**：Chrome 扩展自身运行在浏览器沙箱内

```
archify/flit_stk-architecture.html:5411
Chrome Extension Sandbox — SW + 页面在浏览器隔离沙箱内
```

所有扩展代码（Service Worker、AI 对话页面、popup）都运行在 Chrome 的扩展沙箱中。这是真正的 OS 级进程隔离——Chromium 使用专门的渲染进程、独立的 JavaScript 堆、受限制的 API 访问。

但隔离的对象是**扩展代码本身与浏览器其他标签页**，而不是 AI 与用户文件之间的关系。Chrome 沙箱保护的是浏览器不受扩展侵害，而不是保护用户文件不受 AI 误操作。

### 第 2 层：Chrome FSA 用户手势授权（目录级访问控制）

**来源**：`ai/core/fsa.js`

```js
// fsa.js L1-L11
// 浏览器重启后权限回到 'prompt'，须由用户点击状态条按钮
// （用户手势）内 requestPermission 重新授权。
// 所有路径均为相对所选目录根，过滤 . / .. / 空段防目录穿越。
```

关键机制：
- **用户必须点击选择目录**（Chrome 文件选择器），FSA 才会生成 `DirectoryHandle`
- 权限状态为 `'granted' | 'prompt' | 'denied'` 三态
- 浏览器重启后权限回到 `'prompt'`，必须用户手势重新授权
- 支持多目录管理：主目录 + 附加目录，各自独立授权/移除
- 软链接不可访问（Chromium 安全限制），需添加真实目录为附加根

```js
// fsa.js L213-214
const perm = await workspacePermission(dir.handle);
if (perm !== 'granted') {
    throw new Error('目录权限未授予...');
}
```

**这不是文件系统隔离，而是用户手势授权**——用户必须在每次浏览器启动后通过点击确认，AI 才能访问指定目录。

### 第 3 层：路径穿越防护（相对路径过滤）

**来源**：`ai/core/fsa.js L11`、`flit_bridge/server.js L182-187`

```js
// flit_bridge/server.js
function resolveWorkspacePath(root, relativePath = '') {
    if (!root || !path.isAbsolute(root) || !fs.existsSync(root)) return null;
    const resolved = path.resolve(root, relativePath || '.');
    const relative = path.relative(root, resolved);
    return relative && (relative.startsWith('..' + path.sep) || path.isAbsolute(relative))
        ? null : resolved;
}
```

**原理**：计算目标路径与根目录的**相对偏移**，如果结果以 `..` 开头（说明逃逸了根目录）则拒绝访问。

### 第 4 层：写约束——AI 只能写 `flit/` 目录

**来源**：`README.md L67`、系统提示词规则（`TOOL_GROUP_RULES`）

```
AI 只能写 flit/，读全目录但受 Chrome 授权管辖
```

具体规则：
- **写操作**（`write_file`、`append_file`）：只能写入 `flit/` 目录下
- **读操作**（`read_file`、`list_dir`）：可读取整个已授权工作目录
- **执行操作**（`run_workspace_process`）：可在工作目录内执行已有脚本，但 cwd 受 flit_bridge 校验
- `save_workspace_database_config` 只能写入 `flit/config.json`
- `record_workspace_memory` 只能追加到 `flit/memory.md`
- 工作流只能创建在 `flit/workflow/` 下

**这不是文件系统隔离，而是应用层的写路径约束**。
### 第 5 层：flit_bridge 访问控制（本地回环 + workspace_root 校验）

**来源**：`flit_bridge/server.js`

```js
HOST = '127.0.0.1';  // 只监听本地回环
PORT = 17321;
```

限制：
- 只监听 `127.0.0.1`，不接受外部网络请求
- 所有请求必须传递 `workspace_root` 参数
- `workspace_root` 必须是**绝对路径且真实存在**的目录
- 如果路径不存在或不是绝对路径，直接返回错误

```js
// workspaceContext 函数
if (!root || !path.isAbsolute(root) || !fs.existsSync(root))
    return error('workspace_not_found', ...);
```

### 第 6 层：程序白名单（仅限 6 类可执行文件）

**来源**：`flit_bridge/server.js L154-157`

```js
function allowedProgram(program) {
    const name = path.basename(program).toLowerCase();
    return ['docker', 'docker.exe', 'git', 'git.exe',
            'node', 'node.exe', 'npm', 'npm.cmd',
            'psql', 'psql.exe',
            'python', 'python.exe', 'python3', 'python3.exe']
        .includes(name);
}
```

关键限制：
- **无 Shell**：`shell: false`，禁止通过 shell 执行任意命令
- 白名单仅限 6 种程序：`docker`、`git`、`node`、`npm`、`psql`、`python`
- 只按 `basename` 匹配（防路径注入）
- 超时限制：默认 10 秒，最大 300 秒
- 临时进程注册到 `running` Map，支持取消
- 禁止用 `run_workspace_process` 启动 `flit_bridge` 自身（桥接规则硬约束）

### 第 7 层：SQL 只读（仅 SELECT/WITH/EXPLAIN）

**来源**：`flit_bridge/server.js` databaseQuery 实现

数据库查询通过 `docker exec -i <container> psql` 执行，**仅允许 SELECT、WITH、EXPLAIN 三种 SQL 前缀**，禁止 INSERT/UPDATE/DELETE/ALTER/DROP/CREATE 等写操作。

### 第 8 层：输出 Guard（反编造内容拦截）

**来源**：`ai/core/ai_guard.js`

这是输出侧的最后一道防线，拦截模型编造的行情数据（参见《上下文压缩与跨轮数据保留机制》）。三态决策：
- `pass`：正常放行
- `correct`：注入强制纠正指令，要求重新取数
- `drop`：丢弃编造正文

## 四、与传统沙箱的对比总结

| 维度 | 传统沙箱（Docker/chroot） | flit_stk 沙箱机制 |
|:---|:---|:---|
| **文件系统隔离** | 独立 Namespace，进程看不到外部文件 | ❌ 无隔离；AI 可见已授权目录的全部文件，但受路径校验约束 |
| **进程隔离** | 容器内进程与宿主机隔离 | ✅ Chrome Extension Sandbox 提供进程级隔离 |
| **权限模型** | 基于 UID/GID、Capability | 基于**用户手势授权**（FSA） + **应用层白名单** |
| **写保护** | 容器文件系统层（ReadOnly 层） | 应用层约束（只能写 `flit/`） |
| **网络限制** | 容器网络 Namespace | flit_bridge 绑定 127.0.0.1 + 外部 API 经 HTTPS |
| **程序执行** | 容器内可执行任意命令 | 白名单制（6 种程序）+ 无 Shell |
| **数据持久化** | 通过 Volume 挂载 | Chrome FSA 直通（用户授权目录） |
| **API 隔离** | 系统调用层过滤（seccomp） | HTTP 接口层校验（workspace_root 验证） |
| **输出过滤** | 无（传统沙箱不过滤输出内容） | ✅ Guard 层（反编造内容拦截） |

**本质区别一句话**：传统沙箱建立的是**安全边界**（信任/非信任区），flit_stk 建立的是**安全链路**（每步操作都有授权校验链）。

## 五、为什么这样设计？

flit_stk 是 Chrome 扩展 + 本地量化分析工具，设计约束与传统沙箱不同：

### 5.1 Chrome 扩展的 API 限制

Chrome 扩展不能直接创建虚拟机、不能运行 Docker daemon、不能操作 cgroups。唯一可用的隔离机制是：
- 浏览器自身进程隔离（不可控）
- File System Access API（用户手势授权）
- 本地 HTTP 服务（127.0.0.1 + 自定义校验）

### 5.2 量化分析场景的需求

量化分析场景需要 AI **访问本地数据资产**（PostgreSQL 数据库中的股票数据、本地脚本），这与传统沙箱的「完全隔离」目标直接冲突：

```
典型场景：AI 分析股票
  1. AI 调 query_local_database
  2. → flit_bridge docker exec psql 执行 SELECT
  3. → 返回数据给 AI
  4. → AI 分析并输出结果
```

**如果做文件系统隔离，AI 反而无法访问用户本地的股票数据库**——这是量化分析的核心资产。

### 5.3 设计哲学：能力授权而非隔离

| 操作 | 所需能力 | 授权方式 |
|:---|:---|:---|
| 读取文件 | 该目录的 FSA Handle | 用户点击选择目录 |
| 写入文件 | 写权限 + `flit/` 路径约束 | FSA Handle + 代码层校验 |
| 执行程序 | 白名单匹配 | flit_bridge 校验 |
| 查询数据库 | 有效的 workspace_root + 只读 SQL | flit_bridge 校验 |
| 输出行情数据 | 本轮已取到真实数据 | Guard 层验证 |

## 六、术语建议

鉴于以上分析，项目文档中使用的「沙箱」一词可能引起误解。如果要更精确地描述这套机制，建议区分以下术语：

| 文档用语 | 实际含义 | 建议场景 |
|:---|:---|:---|
| **Chrome 扩展沙箱** | 浏览器进程隔离 | 提及浏览器级保护时 |
| **能力授权层** | FSA + 路径校验 + 写约束 | 描述文件/目录访问控制时 |
| **flit_bridge 访问控制** | 本地回环 + 白名单 + 只读 SQL | 描述危险操作隔离时 |
| **输出 Guard** | AI 输出内容拦截 | 描述防编造时 |
| **八层安全机制** | 整体安全体系 | 架构概览时 |

当然，在对外宣传（如 README）中继续使用「沙箱隔离」作为简洁易懂的类比也完全合理——前提是内部技术文档能清楚说明其实际实现方式。
